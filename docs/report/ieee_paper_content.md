## Abstract

Deep-learning intrusion detection systems are usually reported as accuracy
figures on benchmark datasets, rarely as systems that act on live traffic.
This paper presents a hybrid CNN-LSTM intrusion detection and prevention
system that classifies sequences of network flows, explains its errors with
SHAP, and blocks attackers through the host firewall in real time. The model
is evaluated on CICIDS2017 with a chronological, leakage-controlled split and
on MU-IoT, real IoT traffic with four whole recordings held out. A random
forest trained on identical examples serves as a fair baseline: it is better
on CICIDS2017 (macro F1 0.780 vs 0.586), whereas the CNN-LSTM is clearly
better on MU-IoT (held-out macro F1 0.676 vs 0.404), where single flow
records are ambiguous and sequences resolve them. A per-class prevention
policy derives confidence thresholds from measured F1 and locks unreliable
classes to human review; on the CICIDS2017 test set it acts automatically on
96.6% of attack windows and on 0.33% of benign windows. A packet-to-flow
extractor reproduces CICFlowMeter-V3 features on 99.8% of flows from the
original CICIDS2017 capture. In a live run on a shared Wi-Fi network, a real
port scan was detected about two seconds after its first probes and the
scanning device was blocked automatically, while another user's falsely
flagged device was refused. The limitations of a 2017-trained model on
present-day traffic are measured and reported.

## I. Introduction

Network intrusion detection systems (NIDS) based on machine learning are
commonly evaluated by accuracy on public datasets. Such figures can be
misleading: neighbouring flows in a capture are often near-identical, so
random train/test splits reward memorisation [6], [7], and benign traffic
dominates the data, so accuracy hides failures on rare attacks. A detector
that is to protect a network must also run on live traffic and act on its
decisions, which raises a question benchmark scores do not answer: when may
a model's prediction be trusted to block a device automatically?

This work builds and evaluates a complete system around a hybrid CNN-LSTM
model that reads windows of consecutive flows. The contributions are:

1. **A leakage-controlled evaluation** of the CNN-LSTM on two datasets,
   CICIDS2017 and MU-IoT, against a random-forest baseline trained and
   tested on identical examples, showing where sequence modelling helps and
   where it does not.
2. **An explainability analysis** that uses SHAP to separate three causes of
   the model's errors on unseen IoT recordings.
3. **A prevention layer** in which each class's automatic-action threshold
   follows its measured F1, unreliable classes are locked to human review,
   and execution is bounded by a kill switch, an address allow-list and
   one-rule-per-device bookkeeping.
4. **A live capture pipeline** whose packet-to-flow extractor is validated
   against the original CICIDS2017 capture (99.8% agreement), with a live
   engine that detects and blocks in real time.
5. **A real-network demonstration** with its failure modes reported: a port
   scan detected and blocked in about two seconds, and the false alarms a
   2017-trained model raises on present-day IPv6 and QUIC traffic.

## II. Related Work

**Deep learning for intrusion detection.** Vinayakumar et al. [3] compared
deep neural networks with classical classifiers across several intrusion
datasets and found deep models competitive. Hybrid convolutional-recurrent
models are a common choice for flow sequences, convolution capturing local
patterns between neighbouring flows and recurrence capturing their
development. This work uses such a hybrid but measures it against a strong
classical baseline on identical examples.

**Datasets and their pitfalls.** CICIDS2017 [1] provides labelled flows
generated by CICFlowMeter [2] from a testbed with benign users and fourteen
attack types. Engelen et al. [4] documented artefacts in CICFlowMeter's flow
construction, such as "TCP appendix" flows created after a connection's
FIN, and labelling errors. Sommer and Paxson [6] argued that network
intrusion detection differs from other machine-learning tasks in the cost of
errors and in the gap between training and deployment traffic; Arp et al.
[7] catalogued pitfalls such as data snooping and inappropriate baselines.
The evaluation design here follows these lessons: a chronological split, a
baseline on identical examples, and measurement on real traffic.

**Explainability.** SHAP [5] attributes a prediction to its input features
with additive, game-theoretic contributions. It is used here not to justify
correct predictions but to diagnose wrong ones.

## III. Datasets and Evaluation Design

**CICIDS2017.** Fifteen classes (benign plus fourteen attacks) over five
capture days. Twenty features were selected by random-forest importance.
Because neighbouring flows are often near-identical, the data were split
chronologically within each (capture day, class) group: the first 80% of
rows train, the remainder test. A pure day-level split was rejected because
it removed eight of fifteen classes from the test set. Windows of ten
consecutive flows never span two days, and the scaler is fitted on training
rows only. The test set holds 530,951 windows, 83% benign.

**MU-IoT.** Real IoT traffic in seven classes (normal, DDoS, Injection,
MiTM, Password_Hacking, Scan, Spyware), 3.94 million rows and 38 features
[8]. Flow timestamps were removed because each recording holds one class and
its own time range, so timestamps would reveal the label. Twenty-row windows
never cross a recording block, a split or a gap in row identifiers. Two test
tracks are used: *within* (later traffic of recordings seen in training) and
*held-out* (four whole recordings never seen: an hping3 UDP flood, a
vulnerability scan, an MQTT dictionary attack and an XSS attack). Headline
scores count only test windows whose exact sequence never appears in
training.

**Baseline.** A random forest (100 trees) is trained on single flows with
the same features and split, and scored on the last flow of each CNN-LSTM
test window, so both models are judged on identical examples and labels.

## IV. Model

The same architecture serves both datasets (TABLE I). Two one-dimensional
convolution blocks learn local patterns across neighbouring flows; an LSTM
summarises their development across the window.

**TABLE I — CNN-LSTM ARCHITECTURE**

| Layer | CICIDS2017 | MU-IoT |
|---|---|---|
| Input | 10 flows × 20 features | 20 flows × 38 features |
| Conv1D 64, kernel 3, ReLU; BatchNorm; MaxPool 2 | ✓ | ✓ |
| Conv1D 128, kernel 3, ReLU; BatchNorm; MaxPool 2 | ✓ | ✓ |
| LSTM, 64 units | ✓ | ✓ |
| Dense 64, ReLU | ✓ | ✓ |
| Dense, softmax | 15 classes | 7 classes |
| Parameters | 83,919 | 86,855 |

Both models use Adam, sparse categorical cross-entropy, batch size 512 and
early stopping on validation loss (patience 5). For CICIDS2017, three
class-weighting schemes were compared on the same test set; square-root
balanced weights gave the best result (accuracy 0.984, macro F1 0.586,
against 0.883 / 0.428 for capped balanced weights). MU-IoT training draws a
fresh sample of up to 300,000 windows per class each epoch with
square-root-balanced weights capped at 10, in mixed precision.

## V. Prevention Layer

**Policy.** Each class maps to an action, a severity and a confidence
threshold. Thresholds rise as a class's test F1 falls, from 0.55 (DDoS,
DoS Hulk) to 0.78 (SSH-Patator). Below its threshold a prediction is held
for human review. Classes whose evidence is too weak never act
automatically: on CICIDS2017, Bot, Web Attack – Brute Force and XSS (F1
below 0.15) and SQL Injection, Heartbleed and Infiltration (too few test
examples); on MU-IoT, MiTM and Spyware (no held-out recording). Measuring
the policy changed it: before the lock, all 17 automatic Bot actions on the
CICIDS2017 test set hit benign traffic.

**Execution.** An approved action becomes inbound and outbound Windows
Firewall rules for the attacker's address, added through `netsh advfirewall`.
Execution is bounded by independent checks: a global kill switch (off by
default); an allow-list of RFC 5737 documentation ranges plus single LAN
devices listed explicitly for a demonstration; a deny-list (loopback,
broadcast, unspecified); and an administrator check. One rule is kept per
device whatever class flags it, temporary actions expire on a timer, a
startup sweep recovers state after a crash, and a revoke operation lifts any
block even with the kill switch off. Rate limiting is approximated by a
temporary block, and input sanitisation for XSS stays a recommendation,
since a network firewall cannot perform it.

**Verification.** 35 automated tests cover both policies and every refusal
path; deliberately breaking the engine in 26 ways made a test fail every
time; an end-to-end check on the real firewall passed 22 of 22 checks.

## VI. Live Capture and Validation

**Packet-to-flow extraction.** A new extractor groups packets from a live
interface or a Wireshark capture into bidirectional flows and computes the
twenty features with CICFlowMeter-V3's definitions, including the quirks the
model learned: the first packet counted twice in the packet-length
statistics, sample standard deviations, Ethernet padding counted as payload,
whole-microsecond times, and V3's flow termination rules. It reads IPv4 and
IPv6 from raw bytes at about 68,000 packets per second.

**Validation against the original data.** UNB's original Friday capture was
passed through the extractor and every flow compared with CICFlowMeter-V3's
official row for it (TABLE II). The comparison found two differences, both
corrected: times must be whole microseconds, and a FIN that *starts* a flow
(a TCP appendix [4]) does not end it.

**TABLE II — EXTRACTOR AGAINST CICFLOWMETER-V3 (ORIGINAL CICIDS2017 PCAP, 10 MIN)**

| Measure | Value |
|---|---|
| Flows matched one-to-one with official rows | 5,957 of 7,332 (81%) |
| All 20 features agree (at the CSV's printed precision) | 99.8% |
| All 20 features agree (strictly, within 1e-4) | 86.3% |
| PortScan flows agreeing on all 20 features | 49 of 49 |
| Agreement if flows also end on RST | 98.9% |

**Live engine.** Three threads separate capture, flow tracking and
inference, so bursts of packets never wait for the model. Once per second,
if a flow has ended, the engine classifies the ten most recently ended
flows, selects the target (the most frequent private IPv4 source that sent
traffic to the host, never the host itself or the gateway), and invokes the
firewall engine itself, so blocking does not depend on the dashboard. Live
mode also ends flows on RST: a scan flow (SYN followed by RST) has the same
features either way, and a scan is reported within seconds instead of after
the 120 s flow timeout. A web dashboard shows predictions, executions and
blocked devices with a revoke control.

## VII. Results

### A. Detection on CICIDS2017

**TABLE III — CICIDS2017, 530,951 IDENTICAL TEST EXAMPLES**

| Model | Accuracy | Weighted F1 | Macro F1 |
|---|---|---|---|
| CNN-LSTM (10-flow windows) | 0.984 | 0.986 | 0.586 |
| Random forest (single flows) | 0.991 | 0.991 | 0.780 |

Per class, the CNN-LSTM leads clearly only on DoS Hulk (F1 0.990 vs 0.953).
Both models fail on Bot (0.056 and 0.031), which points to a feature or data
limit. The web attacks fail only for the CNN-LSTM (brute force 0.125 vs
0.688), so the signal exists in single flows and the windowed model loses
it. Large classes are detected well by both (DDoS 0.990, PortScan 0.971 for
the CNN-LSTM).

### B. Detection on MU-IoT

**TABLE IV — MU-IOT, UNSEEN WINDOWS ONLY**

| Measure | CNN-LSTM | Random forest |
|---|---|---|
| Within: accuracy / macro F1 | 0.964 / 0.936 | 0.904 / 0.816 |
| Held-out: accuracy / macro F1 | 0.680 / 0.676 | 0.407 / 0.404 |
| Normal traffic flagged as attack (within) | 9.3% | 17.2% |
| Held-out attacks called normal | 0.09% | 2.5% |

The CNN-LSTM is clearly better, most of all on recordings never seen. It
almost never misses an attack; its held-out errors concern the attack's
name, as unfamiliar tools are mapped to the nearest familiar class. The
reason sequences help here is measurable: with timestamps removed, 71.8% of
single Scan test records also appear in training under another label,
against 0.0% of twenty-row Scan windows.

### C. Error Analysis with SHAP

Expected-gradient SHAP values (validated against `shap.GradientExplainer`,
r = 0.990) were averaged per error group and compared, by cosine
similarity, with correctly classified groups (TABLE V).

**TABLE V — CAUSES OF THE MAIN MU-IOT ERRORS**

| Error | Similarity to predicted class | Similarity to true class | Cause |
|---|---|---|---|
| normal → Spyware | 0.87 | 0.29 | Systematic resemblance |
| hping3 flood → Scan | 0.59 | −0.64 | Real resemblance to scans |
| vulnerability scan → Password_Hacking | 0.20 | −0.05 | Extrapolation beyond training range |

The first error cannot be fixed by a threshold, which is why Spyware is
locked to human review; the second reflects a gap in training coverage; the
third is driven by one feature whose values lie far outside the training
range.

### E. Real Traffic and the Live Run

Three captures were recorded on a phone hotspot with a laptop as the
protected host and a tablet as the second device. In a port scan (`nmap
-sT`, 1,051 probes in 7 s), 98% of the windows pointing at the tablet were
classified PortScan. In laptop browsing, 11.1% of windows were not benign
and 7.6% recommended an automatic action, none of them with a target that
could be blocked; a second, ten-minute browsing capture reached 29.9% non-
benign windows. While the tablet repeatedly loaded a page on the laptop, its
windows were read as Bot and held for review, never executed.

The live run took place on a home Wi-Fi network used daily by 20–30 people,
with the owner's permission and the tablet as the only listed device:

- A real port scan was classified PortScan (confidence 0.99) about two
  seconds after its first probes; the tablet was blocked with one rule, and
  twelve further detections were answered "already blocked".
- The laptop's services became unreachable from the tablet; revoking the
  rule restored access. Three full scan, block and revoke cycles were run.
- Another user's device was classified as a slow-HTTP DoS (confidence
  0.996) from its SSDP discovery broadcasts; the engine refused all ten
  attempts because the device was not listed. Since a broadcasting device
  never addresses the host, targets are now required to have sent traffic
  to it.

Single-window inference takes 1.48 ms on a Ryzen 3 laptop CPU, and batched
inference about 70,700 windows per second.

## VIII. Discussion and Limitations

- **Sequences are not a universal improvement.** They help where single
  flows are ambiguous (MU-IoT) and lose to a single-flow forest where flows
  are distinctive (CICIDS2017).
- **Dataset shift.** The 2017-trained model raises recommendation-only
  false alarms on present-day IPv6 and QUIC traffic (11–30% of browsing
  windows), reads repeated polling as Bot, and recognises a scan only when
  the victim answers it (Windows' stealth mode had to be disabled for the
  demonstration). The safety layers kept all of these from being executed.
- **Scope of the live validation.** One live attack type (a TCP connect
  scan) was run, on one network, from one device. Floods, brute-force and
  web attacks require a victim, vulnerable services or several attacking
  machines on an isolated laboratory network, which were not available;
  these classes were evaluated on recorded data only. Blocking follows
  detection by about two seconds, so a fast scan has already probed most
  ports by then.
- **Evaluation caveats.** Feature selection used a sample that includes some
  later test rows; thresholds come from test-set F1 without a separate
  calibration set; each model was trained once, so scores carry no error
  margin; the extractor was validated on one ten-minute slice of one day.
- **Prevention is deliberately limited** (IPS-lite): it blocks only listed
  devices or documentation addresses, behind a kill switch.

## IX. Conclusion and Future Work

A hybrid CNN-LSTM intrusion detection and prevention system was evaluated
with leakage-controlled splits and a baseline on identical examples, and
taken from benchmark data to live traffic. Its strengths are specific: it
is clearly better than a random forest on ambiguous IoT traffic and on
unseen attack recordings, but not on CICIDS2017. Deriving each class's
automatic-action threshold from its measured F1, and locking unreliable
classes to review, kept automatic action on benign traffic at 0.33% on the
CICIDS2017 test set, and the live run showed real attacks blocked within
seconds while false alarms on other devices were refused. Future work
includes fine-tuning on present-day benign traffic (IPv6, QUIC), evaluating
further attack types live on an isolated laboratory network, a separate
calibration set for the thresholds, and repeated training runs to report
score variance.
